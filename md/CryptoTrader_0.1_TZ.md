## 1. Назначение документа

Документ определяет требования к первой версии CryptoTrader — модульной торговой платформе для алгоритмической торговли криптовалютами через API централизованных бирж.

ТЗ предназначено для:

- проектирования архитектуры и структуры .NET Solution;
- реализации доменной модели, интеграций и торгового ядра;
- разработки Backtesting и Paper Trading;
- последующего подключения реального исполнения ордеров;
- расширения платформы новыми биржами и стратегиями;
- возможного развития продукта в коммерческое ПО или SaaS.

ТЗ фиксирует целевой объём версии 0.1. Оно не означает, что все описанные в разделе «Будущее развитие» возможности должны быть реализованы в первой поставке.

## 2. Цели и исходные условия

### 2.1. Цели продукта

1. Создать расширяемую платформу для автоматизированной торговли криптовалютами.
2. Поддержать Spot и линейные Futures в единой доменной модели.
3. Обеспечить подключение нескольких бирж через унифицированные интерфейсы.
4. Реализовать полный цикл стратегии: рыночные данные → сигнал → риск-проверка → заявка → исполнение → учёт результата.
5. Предоставить воспроизводимый Backtesting и Paper Trading.
6. Обеспечить возможность безопасного постепенного перехода к Live Trading.
7. Не связывать торговое ядро с конкретной биржей, стратегией или способом исполнения.
8. Сохранить архитектурную возможность коммерциализации продукта в будущем.

### 2.2. Предпочтения и ограничения проекта

| Параметр | Требование |
|---|---|
| Планируемый стартовый капитал | Эквивалент $500–2 000; не является гарантированным объёмом средств на счету |
| Рынок | Криптовалюты |
| Инструменты | Spot и Futures |
| Стратегии в перспективе | Скальпинг, Day Trading, Swing Trading, арбитраж |
| Биржи | Несколько, через отдельные адаптеры |
| Основной язык | C# |
| Дополнительный язык | Python для исследований и аналитики, не для торгового ядра MVP |
| Архитектура | Модульный монолит, Clean Architecture, DDD там, где это оправдано |
| База данных | PostgreSQL |
| Развёртывание | Docker Compose на одном VPS или локальном сервере |
| Цель использования | Личная торговля с возможностью последующей коммерциализации |

### 2.3. Ключевые архитектурные решения

- На первом этапе используется **модульный монолит**, а не микросервисная архитектура.
- Рыночные данные и исполнение изолируются от стратегий через интерфейсы.
- Стратегия формирует торговое намерение/сигнал, но не имеет доступа к биржевому API и не отправляет ордера напрямую.
- Любая заявка проходит через Risk Manager и Execution Engine.
- Backtest, Paper и Live используют общие модели сигналов, риск-проверок и жизненного цикла ордера; различаются адаптеры данных и исполнения.
- Реальное исполнение по умолчанию выключено конфигурацией.
- В версии 0.1 реальное исполнение допускается только для Spot после отдельного прохождения критериев допуска. Futures в 0.1 — только Paper/Testnet.
- Приоритет — надёжность, воспроизводимость и контроль риска, а не минимальная задержка уровня HFT.

## 4. Границы версии 0.1

### 4.1. Входит в MVP

1. .NET Solution с разделением Domain, Application, Infrastructure, Host и Exchange Adapter.
2. Единая доменная модель Spot и Futures.
3. Подключение одного биржевого адаптера первой очереди — Bybit API, при условии подтверждённой доступности нужных функций для конкретного аккаунта и юрисдикции.
4. Возможность подключить второй адаптер без изменения доменной модели и стратегий; сам адаптер OKX может быть реализован следующим инкрементом.
5. Получение и нормализация публичных рыночных данных:
   - список инструментов и торговые ограничения;
   - тикеры;
   - исторические свечи;
   - WebSocket-потоки свечей и/или сделок;
   - стакан — интерфейс и базовая реализация, если это необходимо выбранной стратегии.
6. Сохранение свечей и основных справочных данных в PostgreSQL.
7. Загрузка исторических OHLCV-данных.
8. Механизм стратегий и первая стратегия Trend Following / Swing Trading.
9. Набор базовых индикаторов: EMA, RSI, ATR.
10. Risk Manager с расчётом размера позиции и проверкой лимитов.
11. Backtesting на свечных данных с комиссиями и моделью проскальзывания.
12. Paper Trading с использованием потока реальных рыночных данных.
13. Журнал сигналов, решений Risk Manager, заявок и симулированных исполнений.
14. Базовый ASP.NET Core API для просмотра состояния и управления режимом/стратегиями.
15. Логирование, health checks и базовые метрики.
16. Docker Compose для запуска приложения и PostgreSQL.
17. Автоматизированные unit-, integration- и contract-тесты.

### 4.2. Ограничено в MVP

- Реальная торговля Spot может быть включена только явным флагом конфигурации после прохождения критериев допуска из раздела 16.
- Futures поддерживаются доменной моделью, рыночными данными и Paper/Testnet, но реальное Futures-исполнение в версии 0.1 запрещено.
- Поддержка нескольких бирж обеспечивается архитектурно; первая поставка не обязана содержать полноценные адаптеры всех бирж.
- Для первой стратегии достаточно ограниченного набора инструментов и таймфреймов; масштабирование на сотни инструментов не является целью MVP.
- Веб-интерфейс может быть минимальным или заменён Swagger/OpenAPI и простыми страницами статуса. Полноценная Blazor-панель не является блокирующим требованием 0.1.

### 4.3. Не входит в версию 0.1

- Скальпинг и стратегии, требующие надёжной реконструкции очереди заявок.
- Межбиржевой арбитраж с автоматическим исполнением на нескольких площадках.
- Треугольный арбитраж с атомарной или гарантированно согласованной серией ордеров.
- Автоматическая торговля Futures на реальном счёте.
- Маржинальная торговля с кредитным плечом выше 1x.
- Машинное обучение и автономная оптимизация стратегий.
- Автоматический подбор стратегии для Live Trading.
- Управление средствами или API-ключами сторонних пользователей.
- Биллинг, подписки, multi-tenancy и коммерческий SaaS.
- Мобильное приложение.
- Kafka, RabbitMQ, Kubernetes и обязательный Redis.

## 5. Пользовательские сценарии

### 5.1. Подключение биржи

1. Администратор задаёт тип биржи и режим подключения (Public, Testnet/Demo или Live).
2. Для приватных методов добавляет API-ключ и секрет через защищённый механизм конфигурации.
3. Система проверяет доступность API и разрешения ключа.
4. Система загружает сведения об аккаунте и доступных инструментах.
5. Подключение получает статус: `Connected`, `Degraded`, `Disconnected` или `ConfigurationError`.

### 5.2. Получение рыночных данных

1. Market Data Service подключается к публичному WebSocket.
2. Подписывается на инструменты и каналы.
3. Преобразует биржевые сообщения в нормализованные события.
4. Проверяет корректность данных и временные метки.
5. Передаёт события подписчикам и сохраняет необходимые данные.
6. При разрыве соединения переподключается, восстанавливает подписки и при необходимости догружает пропуски через REST.

### 5.3. Запуск стратегии в Paper Trading

1. Пользователь выбирает стратегию, инструменты, таймфреймы и параметры.
2. Система проверяет валидность конфигурации.
3. Стратегия получает Market Snapshot и доступные исторические данные.
4. Стратегия формирует ноль или несколько Trade Signal.
5. Risk Manager разрешает или отклоняет сигнал.
6. Одобренное намерение передаётся в Paper Execution Venue.
7. Симулятор рассчитывает исполнение с учётом заданных комиссий и проскальзывания.
8. Обновляются виртуальные баланс, заявки и позиции.
9. Результат сохраняется и отображается в журнале.

### 5.4. Backtesting

1. Пользователь задаёт диапазон дат, инструменты, таймфреймы, версию стратегии и параметры.
2. Система проверяет полноту данных.
3. Backtesting Engine последовательно воспроизводит рыночные события по времени.
4. Стратегия получает только данные, доступные на соответствующий момент времени.
5. Исполнение симулируется по явно заданной модели.
6. Рассчитываются метрики доходности, риска и качества исполнения.
7. Сохраняется неизменяемый отчёт с параметрами и версией кода стратегии.

### 5.5. Остановка

- Остановка стратегии запрещает создавать новые заявки.
- Отдельная операция позволяет отменить открытые заявки.
- Закрытие открытых позиций является отдельным явным действием и не должно происходить автоматически при обычной остановке процесса.
- Emergency Stop запрещает новые сделки и запускает заданную политику по открытым ордерам/позициям. Политика должна быть конфигурируемой и документированной.

## 6. Архитектурные принципы и best practices

### 6.1. SOLID

**S — Single Responsibility Principle**

- Каждый класс отвечает за одну причину изменения.
- Exchange Adapter не рассчитывает индикаторы.
- Strategy не управляет подключениями и не отправляет ордера.
- Risk Manager не хранит биржевые секреты.
- Repository отвечает за сохранение/чтение данных, а не за бизнес-решения.

**O — Open/Closed Principle**

- Новая биржа добавляется отдельным адаптером.
- Новая стратегия добавляется отдельной реализацией контракта стратегии.
- Добавление нового типа исполнения не должно требовать переписывания стратегий.
- Расширение через композицию и интерфейсы предпочтительнее наследования больших базовых классов.

**L — Liskov Substitution Principle**

- Любой Exchange Adapter обязан выполнять семантический контракт интерфейса, а не только совпадать по сигнатурам.
- Если биржа не поддерживает функцию, адаптер должен явно сообщить `NotSupported`/capability, а не возвращать фиктивное успешное значение.
- Paper и Live реализации должны одинаково трактовать общие доменные инварианты.

**I — Interface Segregation Principle**

- Не создавать один огромный `IExchangeClient` с десятками методов.
- Разделить контракты на `IMarketDataClient`, `ITradingClient`, `IAccountClient`, `IInstrumentMetadataProvider` и, при необходимости, `IFundingRateProvider`.
- Стратегии получают только нужные им данные через `StrategyContext`.

**D — Dependency Inversion Principle**

- Domain и Application зависят от абстракций.
- Infrastructure и Exchange Adapters реализуют порты, определённые внутренними слоями.
- Конкретные SDK бирж регистрируются только в Composition Root.
- Domain не ссылается на EF Core, ASP.NET Core, Bybit.Net, OKX.Net или внешние API SDK.

### 6.2. DDD (Domain-Driven Design)

Использовать DDD прагматично, а не создавать агрегаты и доменные события для каждой таблицы.

**Предлагаемые bounded contexts:**

1. **Market Data** — инструменты, котировки, свечи, сделки, стакан, funding rates.
2. **Trading** — заявки, исполнения, позиции и торговый жизненный цикл.
3. **Risk Management** — лимиты, риск-профили, решения о допуске сделки.
4. **Strategy Management** — определения стратегий, конфигурации и экземпляры.
5. **Backtesting** — запуск теста, модель исполнения и результаты.
6. **Exchange Connectivity** — подключения, возможности бирж и маппинг внешних символов.

**Ключевые агрегаты/корни агрегатов:**

- `TradingAccount` — подключение к торговому аккаунту и его режим.
- `Order` — состояние одной заявки и допустимые переходы состояний.
- `Position` — состояние позиции в рамках аккаунта и инструмента.
- `StrategyInstance` — конфигурация и состояние отдельного запуска стратегии.
- `BacktestRun` — параметры, версия стратегии, диапазон данных и результат теста.
- `RiskProfile` — лимиты и параметры допуска.

Не объединять весь портфель, все заявки и все позиции в один гигантский агрегат. Между агрегатами использовать идентификаторы и прикладные сервисы/доменные события.

**Value Objects:**

- `InstrumentId`
- `ExchangeId`
- `Money` (с валютой)
- `Price`
- `Quantity`
- `Timeframe`
- `OrderType`
- `TradingMode`
- `RiskLimit`

**Domain Events:**

- `MarketEventReceived` — инфраструктурное событие, не обязательно доменное.
- `TradeSignalGenerated`
- `RiskCheckApproved`
- `RiskCheckRejected`
- `OrderSubmitted`
- `OrderAccepted`
- `OrderPartiallyFilled`
- `OrderFilled`
- `OrderCanceled`
- `PositionOpened`
- `PositionChanged`
- `PositionClosed`
- `RiskLimitTriggered`

События должны иметь `EventId`, `OccurredAtUtc`, `CorrelationId` и при необходимости `CausationId`.

### 6.3. Clean Architecture и управление зависимостями

- Направление зависимостей — внутрь, к Domain.
- `Domain` не зависит от других проектов Solution.
- `Application` зависит от `Domain` и внутренних контрактов.
- `Infrastructure` реализует persistence, security, time, messaging и другие порты.
- Exchange Adapter реализует контракты подключения и преобразует внешние DTO в доменные/прикладные модели.
- `Host` является Composition Root: здесь регистрируются зависимости, конфигурация и фоновые сервисы.
- Не использовать Service Locator и доступ к `IServiceProvider` из доменной логики.

### 6.4. Дополнительные инженерные принципы

- **KISS:** не добавлять инфраструктуру без измеримой необходимости.
- **YAGNI:** не реализовывать SaaS, ML и микросервисы до появления соответствующей потребности.
- **DRY:** устранять дублирование бизнес-правил, но не создавать чрезмерно абстрактные универсальные фреймворки.
- **Composition over inheritance:** предпочитать композицию.
- **Explicit over implicit:** режим торговли, риск-лимиты и типы исполнения должны быть явными.
- **Fail safe:** при неизвестном состоянии запрещать новые сделки до восстановления согласованности.
- **Immutable data where practical:** рыночные события, сигналы и отчёты тестов предпочтительно представлять неизменяемыми типами.
- **Idempotency:** повторная обработка одного события/команды не должна создавать повторные торговые операции.
- **Observability:** важные действия должны быть трассируемы через корреляционные идентификаторы, логи и метрики.
- **Configuration as code:** настройки стратегии и среды должны быть версионируемыми и воспроизводимыми.

## 7. Технологический стек

| Область | Решение для 0.1 | Примечание |
|---|---|---|
| Runtime | .NET 10 LTS | Зафиксировать текущий patch SDK через `global.json` и обновлять ежемесячно |
| Язык | C# | Nullable Reference Types включены |
| Web/API | ASP.NET Core Minimal API или Controllers | Выбрать один стиль и придерживаться его |
| Background processing | Generic Host, `BackgroundService` | Для ingestion, backtest jobs и paper trading |
| Биржевые API | REST + WebSocket | Нативный API через отдельные адаптеры |
| Кандидат SDK | Bybit.Net / CryptoExchange.Net | Перед фиксацией версии проверить поддержку нужных endpoints, лицензию и активность проекта; прямой REST/WebSocket-клиент должен оставаться возможным |
| Persistence | PostgreSQL | Основное хранилище |
| ORM | EF Core + Npgsql | Для конфигураций и транзакционных сущностей |
| Bulk data | Npgsql binary COPY / пакетные вставки | Для исторических свечей и массовой загрузки |
| Logging | Serilog | Структурированные логи |
| Metrics / Tracing | OpenTelemetry | Метрики и трассировка |
| API documentation | OpenAPI/Swagger | Для локального и административного API |
| Testing | xUnit, FluentAssertions или Shouldly, Testcontainers | Версии пакетов фиксируются централизованно |
| Deployment | Docker Compose | Один хост на старте |
| Python | pandas, NumPy и инструменты исследования | Только отдельная аналитическая среда, не обязательна для 0.1 |

.NET 10 выбран как LTS-релиз, поддерживаемый Microsoft до 14 ноября 2028 года. Фактическую версию SDK и NuGet-пакетов фиксировать в репозитории; не использовать плавающие версии в production-сборке. [Официальная политика поддержки .NET](https://dotnet.microsoft.com/en-us/platform/support/policy).

## 9. Доменная модель

### 9.1. Инструменты

Поддерживаемые типы:

```csharp
public enum InstrumentType
{
    Spot = 1,
    LinearPerpetual = 2
}

public sealed record InstrumentId(string Value);
public sealed record ExchangeId(string Value);

public sealed record Instrument(
    InstrumentId Id,
    ExchangeId Exchange,
    string ExchangeSymbol,
    string BaseAsset,
    string QuoteAsset,
    InstrumentType Type,
    decimal PriceTick,
    decimal QuantityStep,
    decimal MinQuantity,
    decimal? MinNotional,
    decimal? ContractMultiplier,
    bool IsTradingEnabled);
```

`InstrumentId` — внутренний устойчивый идентификатор. `ExchangeSymbol` — символ в формате биржи. Нельзя считать, что одинаковые строки тикера на разных площадках всегда означают одинаковые условия контракта.

### 9.2. Денежные и числовые типы

- Использовать `decimal` для цен, количеств, комиссий, балансов и денежных расчётов.
- Не использовать `double` для расчёта финансовых сумм.
- Хранить код валюты/актива рядом со значением.
- Определить правила округления цены и количества по metadata инструмента.
- Все даты хранить и передавать как UTC (`DateTimeOffset`).
- Не использовать `DateTime.Now` напрямую в бизнес-логике; внедрять `TimeProvider`.

### 9.3. Свеча

```csharp
public sealed record Candle(
    ExchangeId Exchange,
    InstrumentId Instrument,
    Timeframe Timeframe,
    DateTimeOffset OpenTimeUtc,
    DateTimeOffset CloseTimeUtc,
    decimal Open,
    decimal High,
    decimal Low,
    decimal Close,
    decimal Volume,
    bool IsClosed);
```

Свеча с `IsClosed = false` является предварительной и не должна автоматически использоваться стратегией, рассчитанной на закрытие свечи, пока стратегия явно не поддерживает внутрисвечные сигналы.

### 9.4. Заявка и исполнение

Заявка должна включать:

- внутренний `OrderId`;
- `ClientOrderId` для идемпотентности;
- аккаунт и биржу;
- инструмент;
- тип рынка (Spot/Futures);
- сторону (Buy/Sell);
- тип ордера (Market/Limit и поддерживаемые дополнительные типы);
- количество;
- цену для Limit;
- ReduceOnly для поддерживаемых Futures-операций;
- время создания/обновления;
- внешний `ExchangeOrderId`;
- статус и причину отказа.

Состояния заявки как минимум: `PendingSubmit`, `Submitted`, `Accepted`, `PartiallyFilled`, `Filled`, `CancelPending`, `Canceled`, `Rejected`, `Unknown`.

Переходы состояний должны контролироваться доменной моделью. Нельзя переводить `Filled` обратно в `Submitted` или считать timeout доказательством отказа биржи.

Исполнение (`Execution`) хранится отдельно от заявки, поскольку одна заявка может быть исполнена несколькими частями.

### 9.5. Позиция

Позиция должна содержать:

- аккаунт, биржу и инструмент;
- Spot/Futures тип;
- сторону;
- количество;
- среднюю цену входа;
- реализованный и нереализованный PnL;
- комиссии и funding payments;
- маржу и параметры плеча для Futures;
- время открытия/последнего изменения.

В версии 0.1 расчёт PnL должен быть детерминированным и покрыт тестами. Не смешивать денежный баланс Spot и маржинальное состояние Futures.

## 11. Стратегия первой версии: Trend Following / Swing Trading

### 11.1. Назначение

Первая стратегия нужна для проверки сквозного торгового цикла и не заявляется как гарантированно прибыльная.

Предлагаемый базовый вариант:

- старший таймфрейм: 4h;
- рабочий таймфрейм: 1h;
- индикаторы: EMA 50, EMA 200, RSI 14, ATR 14;
- начальный инструментальный набор: BTC/USDT и ETH/USDT, если они доступны и соответствуют ограничениям аккаунта;
- первая реализация: Long-only Spot;
- Futures-сигналы могут тестироваться в симуляторе позднее.

### 11.2. Базовая логика для первой проверяемой версии

Пример начальной конфигурации, параметры должны быть изменяемыми:

1. На 4h EMA 50 должна быть выше EMA 200.
2. Цена закрытия 4h должна быть выше EMA 200.
3. На 1h RSI 14 ранее опускался ниже заданного порога (например, 40) и пересекает этот порог вверх на закрытии свечи.
4. Сигнал создаётся только на закрытой 1h-свече.
5. Предлагаемая цена входа для Backtest — цена следующего доступного открытия свечи, а не уже известная цена закрытия сигнальной свечи.
6. Stop Loss рассчитывается от ATR, например `Entry - ATR * 2` для Long.
7. Take Profit и/или выход по развороту трендового условия настраиваются конфигурацией.
8. Сигнал отклоняется, если ожидаемый риск/доходность, минимальный размер сделки или доступный баланс не соответствуют настройкам.

Параметры являются стартовой гипотезой для исследования. Они не должны считаться оптимальными и не могут оптимизироваться на том же периоде, на котором оценивается итоговая эффективность.

### 11.3. Защита от look-ahead bias

- Стратегия не видит незакрытые будущие свечи.
- Индикатор использует только данные с временем не позже момента сигнала.
- Исполнение не происходит по цене, которая была известна только после момента принятия решения.
- При использовании нескольких таймфреймов старшая свеча должна быть закрыта к моменту сигнала.
- Пропущенные данные не должны незаметно заменяться будущими значениями или интерполяцией, создающей ложный сигнал.

## 12. Risk Management

### 12.1. Начальные ограничения

Стартовые значения для Paper Trading и осторожной проверки — конфигурируемые, а не зашитые в код:

| Параметр | Стартовое значение |
|---|---:|
| Риск на одну сделку | 0,25–0,5% equity |
| Дневной лимит потерь | 1% equity |
| Максимум одновременно открытых позиций | 2 |
| Futures leverage | 1x в симуляции, без Live Futures в 0.1 |
| Cross Margin | Запрещён для будущего первого этапа Futures |
| Усреднение убыточной позиции | Запрещено по умолчанию |
| Разрешение на вывод средств через API | Никогда не запрашивать и не использовать |

Все параметры должны иметь валидацию и храниться в конфигурации профиля риска с историей изменений.

### 12.2. Расчёт размера позиции

Для линейного Spot-приближения:

```text
RiskAmount = Equity * RiskPercent
UnitRisk = abs(EntryPrice - StopLossPrice)
RawQuantity = RiskAmount / UnitRisk
ApprovedQuantity = NormalizeDown(RawQuantity, Instrument.QuantityStep)
```

Затем проверить:

- комиссию входа и предполагаемого выхода;
- проскальзывание;
- минимальное количество и минимальный notional;
- доступный баланс;
- общий лимит экспозиции;
- корреляционную/концентрационную нагрузку, если она реализована.

Для Futures требуется отдельный расчёт с учётом контрактного множителя, маржи, funding, maintenance margin и цены ликвидации. Нельзя применять Spot-формулу без адаптации.

### 12.3. Обязательные предохранители

- `MaxDailyLoss` — запрет новых сделок после достижения дневного лимита.
- `MaxDrawdown` — остановка стратегии/торговли при превышении допустимой просадки.
- `MaxPositionSize` и `MaxPortfolioExposure`.
- `MaxOpenPositions`.
- `ExchangeHealthGuard` — запрет новых сделок при потере соединения или устаревших данных.
- `DuplicateOrderGuard` — уникальный ClientOrderId и защита от повторной отправки.
- `UnknownOrderStateGuard` — при неизвестном результате отправки сначала запросить состояние заявки, не отправлять дубль.
- `EmergencyStop` — глобальный запрет новых сделок.
- `StaleMarketDataGuard` — не торговать на устаревших данных.
- `InstrumentTradingStatusGuard` — проверка статуса инструмента и торговых ограничений.

### 12.4. Fail-safe поведение

При неопределённом состоянии:

- новые заявки запрещаются;
- уже открытые позиции не считаются закрытыми;
- статус аккаунта сверяется с биржей;
- событие ошибки и причина блокировки записываются;
- возобновление происходит только после успешной сверки и снятия блокировки.

## 13. Backtesting и Paper Trading

### 13.1. Backtesting

Входные параметры:

- стратегия и её версия;
- конфигурация стратегии;
- инструмент/биржа;
- диапазон дат;
- таймфрейм;
- начальный капитал;
- модель комиссии;
- модель проскальзывания;
- правила исполнения Stop Loss/Take Profit;
- режим Spot или Paper Futures.

Минимальный отчёт:

- Initial Equity и Final Equity;
- Net Profit и ROI;
- Max Drawdown;
- Profit Factor;
- Win Rate;
- Expectancy;
- Sharpe Ratio и/или Sortino Ratio;
- количество сделок;
- среднее время удержания;
- суммарные комиссии;
- оценка проскальзывания;
- equity curve;
- список сделок;
- версия стратегии и полный набор параметров.

### 13.2. Требования к модели исполнения

- Для свечного Backtest явно документировать допущения о fill price.
- Если внутри одной свечи затронуты и Stop Loss, и Take Profit, использовать консервативное допущение либо перейти к более детальным данным; нельзя произвольно выбирать выгодный исход.
- Учитывать частичное исполнение только при наличии подходящей модели данных; иначе обозначить ограничение отчёта.
- Учитывать maker/taker fee в соответствии с конфигурацией инструмента/аккаунта.
- Не учитывать funding как ноль для Futures, если модель заявляет поддержку funding.
- Отчёт должен показывать, какие упрощения использовались.

### 13.3. Walk-forward и out-of-sample

- Данные делятся на in-sample и out-of-sample по времени.
- Оптимизация параметров выполняется только на in-sample.
- Финальная оценка выполняется на данных, не использованных при подборе параметров.
- Проверять устойчивость параметров к небольшим изменениям.
- Не запускать автоматическую оптимизацию параметров на реальном счёте в версии 0.1.

### 13.4. Paper Trading

Paper Trading получает актуальные рыночные данные, но не отправляет реальные торговые заявки.

Симулятор обязан учитывать:

- доступный виртуальный баланс;
- позиции и заявки;
- комиссии;
- проскальзывание;
- ограничения инструмента;
- частичное исполнение — если включено моделью;
- Stop Loss и Take Profit;
- Funding для симулируемых Futures, если они задействованы.

Paper Trading не является доказательством будущей доходности и может отличаться от реального исполнения.

### 14.2. REST и WebSocket

REST использовать для:

- исторических запросов;
- первоначальной загрузки инструментов и ограничений;
- восстановления состояния аккаунта;
- сверки заявок/позиций;
- точечных запросов.

WebSocket использовать для:

- публичных рыночных потоков;
- приватных обновлений ордеров, исполнений и позиций;
- обновлений баланса, если соответствующий поток поддерживается.

### 14.3. Надёжность подключения

Адаптер обязан обеспечивать:

- heartbeat/ping-pong согласно документации биржи;
- переподключение с exponential backoff и jitter;
- ограничение частоты повторных попыток;
- повторную подписку после reconnect;
- обнаружение пропусков/невалидного sequence для стакана;
- очистку и повторную инициализацию локального order book после потери sequence;
- контроль Rate Limits;
- синхронизацию времени;
- безопасное завершение по `CancellationToken`;
- REST reconciliation после восстановления private stream.

### 14.4. Ограничения доступа и юрисдикции

Доступность биржи, Spot, Futures, API, Testnet/Demo и пополнения может различаться в зависимости от страны проживания, гражданства, резидентства, KYC-статуса и типа аккаунта.

Перед включением адаптера в Live необходимо проверять актуальные официальные Terms of Service, санкционные ограничения, KYC и применимость конкретного продукта. Не обходить географические или санкционные ограничения ложными данными, чужими аккаунтами или маскировкой местоположения.

Поскольку пользователь проекта проживает в РФ, юридическая проверка является обязательным пунктом допуска к Live. Банк России указывает, что с 1 июля 2027 года для резидентов, не являющихся лицами, организующими обращение цифровых валют, действует предусмотренный законом порядок совершения сделок через таких лиц или с ними; отдельные P2P-операции между физическими лицами после этой даты не входят в установленный перечень. Применимость закона к конкретной бирже, продукту и операции должен определить профильный юрист. См. [разъяснения Банка России](https://www.cbr.ru/explan/cryptocurrency/).

## 16. Безопасность

### 16.1. API-ключи

- Не хранить API-ключи и секреты в исходном коде, `appsettings.json`, Git, Docker image или логах.
- Для локальной разработки использовать User Secrets или переменные окружения.
- Для VPS использовать защищённое хранилище секретов либо зашифрованные секреты с отдельным ключом шифрования.
- Ключи должны иметь только необходимые разрешения: чтение и торговля.
- Право вывода средств (withdrawal) не запрашивать и не использовать.
- По возможности ограничить ключи IP-адресом сервера.
- Предусмотреть ротацию и отзыв ключей.
- Маскировать секреты в логах и исключениях.

### 16.2. Защита приложения

- ASP.NET Core API не должен быть публично доступен без аутентификации.
- Для административных операций необходима авторизация.
- CORS ограничить доверенными origin.
- Использовать HTTPS при внешнем доступе.
- Не помещать приватные ключи в ответы API.
- Ограничить частоту административных запросов.
- Регулярно обновлять зависимости и проверять уязвимости.
- Запускать контейнеры без root, где это поддерживается.
- Не публиковать PostgreSQL наружу без необходимости.
- Делать резервные копии БД и проверять возможность восстановления.

### 16.3. Разделение режимов

Режимы `Backtest`, `Paper`, `Testnet/Demo`, `Live` должны быть явными и несовместимые режимы нельзя переключать неявно.

Для включения Live требуются:

1. Явный конфигурационный флаг.
2. Ручное подтверждение при запуске/включении.
3. Успешные health checks.
4. Успешная reconciliation.
5. Проверка лимитов и API permissions.
6. Успешное прохождение критериев допуска.

Конфигурация Live не должна случайно включаться из-за отсутствующего или некорректного значения. Безопасное значение по умолчанию — `false`.

## 20. Нефункциональные требования

### 20.1. Надёжность

- Приложение должно корректно завершаться по SIGTERM/Ctrl+C.
- Фоновые сервисы должны поддерживать `CancellationToken`.
- Обрыв WebSocket не должен приводить к бесконечному циклу быстрых запросов.
- Система должна явно показывать stale market data.
- При потере связи с биржей новые сделки блокируются.
- После перезапуска приложение обязано выполнить восстановление и сверку состояния до разрешения Live-операций.

### 20.2. Производительность MVP

Целевые ориентиры для первого релиза, а не требования HFT:

- обработка потока свечей для начального набора до 20 инструментов без устойчивого роста очередей;
- завершение обработки закрытой свечи и вызова стратегии — до 1 секунды в нормальных условиях на целевом VPS;
- API чтения состояния — p95 до 500 мс при локальном/обычном сетевом доступе и небольшой нагрузке;
- отсутствие потери подтверждённых исполнений при штатном reconnect и последующей reconciliation.

Фактические показатели фиксируются нагрузочными тестами и журналом измерений.

### 20.3. Воспроизводимость

Каждый Backtest обязан хранить:

- идентификатор и версию стратегии;
- полную конфигурацию;
- источник и диапазон данных;
- версию движка тестирования;
- комиссии и slippage model;
- дату запуска;
- итоговые метрики.

Повторный запуск с теми же данными, параметрами и версией движка должен давать идентичный результат в пределах определённой числовой точности.

### 20.4. Поддерживаемость

- Nullable Reference Types включены.
- Публичные контракты документируются XML comments или отдельной документацией.
- Анализаторы .NET включены.
- Для общих правил форматирования использовать `.editorconfig`.
- NuGet-версии централизованы в `Directory.Packages.props`.
- SDK фиксируется через `global.json`.
- Ключевые архитектурные решения фиксируются в ADR.
- Бизнес-логика не должна зависеть от конкретной СУБД или биржи.

## 24. Условия допуска к реальной торговле Spot

Реальная торговля Spot не включается автоматически после завершения разработки. Перед её включением необходимо:

1. Подтвердить законную и фактическую доступность биржи, продукта, аккаунта и API для пользователя.
2. Проверить актуальные условия биржи и применимое законодательство.
3. Успешно выполнить интеграционные тесты на тестовой среде.
4. Провести Paper Trading не менее 30 календарных дней либо получить иной явно утверждённый период с достаточным количеством сделок.
5. Проверить результаты на независимом историческом периоде.
6. Проверить комиссионную модель и фактические торговые комиссии аккаунта.
7. Проверить recovery/reconciliation после принудительного отключения приложения и сети.
8. Убедиться, что API-ключ не имеет права вывода.
9. Включить строгие лимиты по капиталу и дневным потерям.
10. Провести ручную проверку первой сделки и журналирования.

Даже выполнение этих условий не гарантирует прибыльность стратегии. Реальная торговля может привести к полной потере выделенного капитала.

## Приложение A. Нормативное правило для разработчика

**Ни одна стратегия не должна иметь возможность самостоятельно отправить реальную заявку на биржу.**

Единственный допустимый путь торговой операции:

```text
Market Data
    -> Strategy
    -> Trade Signal
    -> Risk Manager
    -> Approved Order
    -> Execution Engine
    -> Execution Venue
    -> Exchange Adapter
    -> Exchange
    -> Order/Execution Updates
    -> Reconciliation
    -> Persistence
```

Нарушение этой последовательности считается архитектурным дефектом.

## Приложение B. Правило выбора режима по умолчанию

```text
Backtest  — разрешён без биржевого аккаунта.
Paper     — разрешён с публичными рыночными данными.
Testnet   — разрешён после настройки тестового аккаунта.
Live Spot — запрещён по умолчанию; только явное включение после допуска.
Live Futures — запрещён в CryptoTrader 0.1.
```

## Приложение C. Критерий качества стратегии

Стратегия не считается успешной только потому, что показывает положительный ROI.

Минимум требуется оценивать:

- результат после всех моделируемых комиссий и проскальзывания;
- максимальную просадку;
- количество сделок и статистическую устойчивость;
- результат вне периода подбора параметров;
- зависимость от конкретного актива, временного периода и рыночного режима;
- отличие Paper-исполнения от ожидаемого реального исполнения.

**Цель CryptoTrader 0.1 — создать надёжную, тестируемую и расширяемую торговую платформу. Получение положительной доходности не является критерием приёмки программного обеспечения и не может быть гарантировано разработкой.**
